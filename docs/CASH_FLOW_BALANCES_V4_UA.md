# Рух коштів: денні залишки та реалізації — V4

Виправлення від 28.10.2026. На WST\WST / portal_db створено окрему dbo.GetDealerFullLedger_4; чинну V3 не змінено. Її визначення до роботи збережено в database/procedures/backups/cashflow_v4_20261028/GetDealerFullLedger_3_before.sql.

## Причина

Фронтенд брав залишок останнього видимого руху попереднього дня або вираховував початковий залишок із видимих приходу/розходу. Реалізації SQL приховував, хоча вони змінювали сальдо основного договору. Через це відображений початок дня не пояснював залишок перед платежем.

Приклад: Мощук Юлія, основний договір:

- після операцій 21.10: 138 167 грн;
- реалізація ЄВ000079099 від 22.10: 7 871 грн; залишок 130 296 грн;
- початок 23.10: 130 296 грн;
- реалізації 23.10: ЄВ000079752 — 1 441 грн; ЄВ000079755 — 6 880,42 грн; ЄВ000080156 — 332,58 грн; разом 8 654 грн;
- перед оплатою о 16:30 23.10: 121 642 грн;
- прихід на основний договір 23.10: 99 823 грн; кінець дня: 221 465 грн.

Отже, різниця між 138 167 та 121 642 — 16 525 грн реалізацій за два дні. Залишок на початок дня не повинен штучно дорівнювати залишку перед пізнішою операцією, якщо протягом дня були реалізації.

## Поведінка V4

DayOpeningSaldo та DayClosingSaldo рахуються за всіма активними рухами регістру договору до фільтрації видимих документів. Сума RealizationAmount береться з рядка регістру; суму заголовка реалізації не повторюємо для кожного рядка. Для реалізацій одна строка метаданих на документ, без недоведеного розподілу на замовлення через ROW_NUMBER. Похідне CumSaldoOrder для грошових рядків через це може відрізнятися від V3; воно не використовується в цих підсумках. Грошові рядки, суми, залишки договорів та їхні інші поля на перевіреному прикладі збіглися.

На комп’ютері є окрема колонка «Реалізації», на телефоні — окрема сума в картці. Реалізації не включаються до грошового розходу чи оплати. У Excel окрема колонка суми реалізації та номера документа. Групування враховує ID договору й валюту, а не лише однакову назву договору.

Локальні API та Excel використовують V4. На робочому сервері код API/фронтенду ще не оновлювався; його поточний API продовжує викликати V3 до розгортання коду. Для іншої копії БД спочатку встановити GetDealerFullLedger_4_linked_server.sql, перевіривши її джерела WST\WST/oknastyle/oknastyle_biV2.

Перевірено: 5 Node-тестів бізнес-розрахунків; 2 Python-тести API/Excel; порівняння 27 грошових рядків V3/V4 на прикладі Мощука; однакові залишки при виборі окремого 23.10 та періоду 21–23.10; суми реалізацій 7871 та 8654; V3 залишилася незмінною. Стандартні постійні індекси не змінювали.

Для розгортання коду потрібні збірка фронтенду та перезапуск backend. Для відкату коду повернути виклики V3 в payments/views.py і попередній фронтенд; вихідна V3 досі доступна. Нової міграції немає.

## Номери замовлень біля реалізації

Додано RealizationOrderNumbers: відсортований список унікальних номерів замовлень з явних посилань заголовка «Сделка», табличної частини «Товары.ЗаказПокупателя» та «ДокументыРасчетовСКонтрагентом.Сделка». Посилання звіряються з довідковими записами документів «ЗаказПокупателя». Список агрегується до одного рядка на реалізацію; кількість рядків руху, всі попередні поля та суми залишилися незмінними на перевірених 31 рядку Мощука за 21–23.10.

Приклади: ЄВ000079099 → 15-04162; ЄВ000079752 → 02-19091; ЄВ000079755 та ЄВ000080156 → 45-179234. Відображення є біля назви реалізації на комп’ютері й телефоні та в колонці «№ зам.» Excel. Якщо явного зв’язку немає, номер не вигадується. Попередню V4 збережено в GetDealerFullLedger_4_before_order_numbers.sql у папці резервних копій.


## Уточнення відображення

За вказівкою користувача окремий стовпець «Реалізації» та окрему суму в мобільній картці прибрано. Реалізація — розхід з договору: сума входить у «Розхід» один раз, назва операції та номери замовлень лишаються в описі. Денний показник «у т. ч. реалізації» є складовою розходу. В Excel реалізація теж у «Розході», а показник «У т. ч. реалізації» інформаційний; як оплату реалізацію не позначаємо.

## Поточний спрощений вигляд

Повну версію перед спрощенням збережено окремо: backups/cashflow_full_20261028_092516/README_UA.md (разом із вихідними файлами UI, Excel, тестами та SQL V4). Поточний екран використовує allocationView: true: реалізації приховані; для договорів «Основной/Основний» показуються лише ППВход/ПКО з підтвердженим номером замовлення. Їхні батьківські суми й залишки, початкові бейджі та денні підсумки договору приховані; деталізація сум рознесення на замовлення залишається доступною. Суми авансових договорів залишаються. Та сама політика діє в Excel: видно суми оплати замовлень, без сальдо основного договору та без реалізацій.

SQL V4 і дані 1С у цьому кроці не змінювали. Зміни підготовлено локально. Перевірено 9 Node-тестами та 3 Python-тестами API/Excel.
