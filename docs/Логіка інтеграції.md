# Логіка інтеграції замірника з порталом

Опис поточного локального коду станом на **28.10.2026**. Версія на робочому сервері залежить від останнього розгортання. Документ описує реалізовану частину порталу Django/React; код Laravel замірника в цьому репозиторії відсутній.

## 1. Схема роботи

```mermaid
sequenceDiagram
    participant U as Користувач
    participant P as Портал React/Django
    participant Z as Замірник Laravel
    participant C as 1С
    U->>P: Відкриває /zamir після входу в портал
    P->>P: Перевіряє роль, строк доступу та email
    P->>Z: Завантажує iframe
    Z-->>P: postMessage zamir:need-login
    P->>P: GET /api/zamir/ticket/ під JWT
    P-->>Z: postMessage zamir:login + підписаний ticket
    Z->>Z: Перевіряє квиток, знаходить/створює акаунт, відкриває свою сесію
    U->>Z: Створює заявку з PDF і необов’язковими фото
    Z->>P: POST /api/integrations/measurement/orders/ із серверним ключем
    P->>P: Перевіряє дилера, дані та ключ повтору
    P->>C: CreateCalculation
    C-->>P: Результат і GUID прорахунку
    P->>P: Зберігає результат у БД порталу
    P-->>Z: HTTP-відповідь із GUID або помилкою
    P->>P: Успіх — повідомлення менеджеру й копія; відмова — бот помилок
```

Дії знаходження/створення акаунта та відкриття сесії виконує Laravel за погодженим протоколом. Django передає підписані дані користувача, а не створює акаунт безпосередньо в БД замірника.

## 2. Доступ і відображення

- Сторінка порталу: `/zamir`.
- Адреса iframe: `https://zamir.viknastyle.com.ua/`.
- Доступ до входу мають активні `admin`, `dealer`, `customer`, `manager`, `region_manager`, `regionalManager`, `branch_manager`, `branches_director`, якщо строк доступу не завершився.
- Окрема роль `director` та невідомі ролі в поточному дозволеному списку SSO відсутні.
- «Замірник» розташований у хедері перед конструктором для дозволених ролей, також є в мобільному меню.
- У звичайному режимі iframe обмежений шириною хедера й розташований під ним. Є кнопка повного екрана; якщо браузер не дозволяє Fullscreen API, використовується розгортання в межах вікна браузера.
- Віджет підтримки на `/zamir` прихований.

**Вхід і право створення заявки — різні дозволи.** Менеджер може увійти у власний акаунт замірника, але API створення відхилить його заявку як заявку недилера.

## 3. Перевірка пошти перед входом

Портал спочатку викликає `GET /api/zamir/profile/` під своєю JWT-авторизацією.

```json
{
  "email": "dealer@example.com",
  "email_required": true
}
```

Форма показується, якщо email порожній, має неправильний формат або `User.EmailConfirmed = 0`. Користувач вводить чи підтверджує актуальну адресу; портал надсилає:

```http
POST /api/zamir/profile/
Authorization: Bearer <JWT порталу>
Content-Type: application/json
```

```json
{ "email": "dealer@example.com" }
```

Сервер перевіряє формат та відсутність такої адреси в іншого користувача без урахування регістру. Оновлюються **лише email поточного користувача та EmailConfirmed**. Параметр чужого ID змінити користувача не дозволяє.

Це підтвердження адреси самим користувачем у формі. Лист із кодом або посиланням для доведення володіння поштою цей механізм не надсилає.

## 4. Квиток входу SSO

Endpoint: `GET /api/zamir/ticket/`.

Авторизація — JWT порталу; один лише `X-API-KEY` не дає доступу до квитка. Перевіряються роль, активність, строк доступу та коректна підтверджена пошта.

Відповідь:

```json
{ "ticket": "<data>.<sig>" }
```

`data` — Base64URL без кінцевих `=` від UTF-8 JSON:

```json
{
  "user_id": 78,
  "email": "dealer@example.com",
  "name": "Ім’я користувача",
  "exp": 1800000060,
  "nonce": "випадкове значення"
}
```

- `user_id` — внутрішній `[portal_db].[dbo].[User].[ID]`, не GUID 1С та не ID Laravel.
- `name` — FullName, а за його відсутності Username.
- `exp` — Unix-час формування квитка + **60 секунд**.
- `nonce` — нове випадкове значення для кожного квитка.
- `sig` — hex від `HMAC-SHA256(data, MEASUREMENT_API_KEY)`.

Пароль користувача та JWT порталу у квиток не входять. Відповідь має `Cache-Control: no-store, private` та `Pragma: no-cache`.

**Квиток у БД Django не зберігається.** Він перевіряється за підписом і строком дії. Django також не веде список використаних nonce: якщо потрібна сувора одноразовість, спожиті nonce має відхиляти Laravel. Наявність nonce сама по собі не доводить, що повторне використання вже заблоковане на стороні замірника.

Laravel має перевірити HMAC, `exp` і прив’язати свій акаунт до `user_id` порталу. Автоматичне створення акаунта при першому SSO-вході та обробка зміни email — відповідальність замірника. Портал не передає роль користувача у квитку; право подання заявки завжди повторно перевіряється на Django.

## 5. Обмін iframe через postMessage

Початковий запит надсилає **замірник**:

```javascript
{ type: 'zamir:need-login' }
```

Портал приймає його тільки за одночасного виконання двох умов:

1. `event.origin === 'https://zamir.viknastyle.com.ua'`;
2. `event.source` — саме вікно поточного iframe замірника.

Після цього React запитує свіжий квиток у Django й відповідає тільки цьому iframe та конкретному origin:

```javascript
{ type: 'zamir:login', ticket: '<data>.<sig>' }
```

Якщо сесія замірника завершилася, він може знову надіслати `zamir:need-login`; портал сформує новий квиток. Паралельні запити квитків у компоненті обмежені прапорцем pending.

Для виходу портал надсилає:

```javascript
{ type: 'zamir:logout' }
```

Відправлення виконується при виході з порталу через AuthProvider, події `pagehide` та від’єднанні iframe при переході з `/zamir` на іншу сторінку порталу. При поверненні iframe створюється заново й проходить SSO.

Це браузерне повідомлення без підтвердження виконання. Воно залежить від обробника Laravel і не є серверним відкликанням усіх сесій замірника в усіх браузерах. Вкладка без iframe не має власного вікна замірника для postMessage.

## 6. Подання заявки із замірника

**Сервер Laravel → сервер порталу:**

```http
POST https://portal.vstg.com.ua/api/integrations/measurement/orders/
Content-Type: application/json
X-API-KEY: <спільний серверний ключ>
Idempotency-Key: <UUID цієї заявки>
```

Логін, пароль і JWT користувача для цього запиту не потрібні. Ключ не повинен потрапляти до JavaScript iframe.

```json
{
  "user_id": 78,
  "items_count": 2,
  "order_number": "zamir-125",
  "comment": "Інформація щодо замовлення",
  "file": {
    "fileName": "zamir-125.pdf",
    "fileDataB64": "BASE64_РЕАЛЬНОГО_PDF"
  },
  "photos": [
    {
      "fileName": "photo-1.jpg",
      "fileDataB64": "BASE64_РЕАЛЬНОГО_ФОТО"
    }
  ]
}
```

Обов’язкові: `user_id`, `items_count >= 1`, PDF `file.fileName` та `file.fileDataB64`. Номер заявки, коментар і фото необов’язкові. Номер можна не передавати або передати порожнім рядком; `null` для нього не підтримується.

PDF — до **20 МіБ**. Фото — до **10 штук**, кожне до **10 МіБ**, JPG/JPEG, PNG, WebP. Перевіряються розширення, Base64 і сигнатура. Base64 передається без `data:`-префікса.

Повний перелік полів, включно з необов’язковими варіантами доставки: [MEASUREMENT_API_UA.md](MEASUREMENT_API_UA.md). Звичайна заявка із замірника може подаватися без адреси.

## 7. Як визначається дилер

Після перевірки `X-API-KEY` Django:

1. Перевіряє додатний цілий `user_id`.
2. Шукає активного користувача порталу з цим ID.
3. Перевіряє строк доступу.
4. Дозволяє створення лише ролям `dealer` та `customer`.
5. Вимагає прив’язку `User.UserId1C` до контрагента.

Якщо роль інша, повертається HTTP `403`:

```json
{ "detail": "Ви не дилер. Створення заявки недоступне." }
```

Якщо немає прив’язки до контрагента, теж повертається `403`. Перевизначення `contractor_guid` чи `contractor_id` у JSON відхиляється. Laravel повинен визначати `user_id` зі свого перевіреного зв’язку з акаунтом порталу, а не з довільного введення в браузері.

## 8. Передавання в 1С та результат

Портал перетворює дані на стандартний `CreateCalculation` для налаштованої робочої публікації `ONE_C_URL`:

- контрагент визначається за користувачем порталу;
- номер замірника передається як номер зовнішньої заявки;
- кількість конструкцій і коментар передаються разом із PDF та фото;
- PDF і фотографії об’єднуються у список файлів для 1С;
- у payload забезпечуються поля `orders` та `address`, навіть якщо замірник не передав адресу.

Серверні облікові дані 1С налаштовані на порталі та не передаються замірнику.

API створює **прорахунок/заявку в 1С**, а не гарантує автоматичне оформлення виробничого замовлення.

При успіху Django повертає HTTP `201`:

```json
{
  "success": true,
  "calculation_guid": "11111111-2222-4333-8444-555555555555",
  "portal_user_id": 78,
  "contractor_guid": "aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeeeee"
}
```

Замірник має зберегти HTTP-код, цю відповідь і GUID біля своєї заявки. Запис `201` у журналі Apache підтверджує сформовану порталом відповідь, але не доводить, що Laravel успішно зберіг її у своїй БД.

## 9. Повтори та збереження результату

Кожна нова заявка має свій UUID `Idempotency-Key`; повтор тієї самої заявки надсилається з тим самим UUID.

Внутрішній ключ Django обчислюється як UUIDv5 від адреси 1С, `user_id` і зовнішнього UUID. Тому записи ізольовані за користувачем та публікацією 1С.

Використовується наявна таблиця `portal_db.dbo.CalculationIdempotencyRecords`:

| Поле | Призначення |
|---|---|
| IdempotencyKey | Внутрішній ключ повтору |
| PayloadHash | Хеш змісту заявки; змінний createdAt виключається |
| Status | sending / succeeded / failed / uncertain |
| CalculationGuid | GUID документа, який повернула 1С |
| ResponseBody | Збережена відповідь, переданий payload і службові стани сповіщень |
| LastError | Остання помилка |
| CreatedAt / UpdatedAt | Час створення й оновлення |

Поточна поведінка коду:

| Стан попередньої спроби | Дія повторного запиту |
|---|---|
| succeeded, той самий зміст | Повертається збережений успіх з HTTP 201; нового відправлення немає |
| succeeded, змінений зміст | HTTP 409 — ключ уже використано для іншої заявки |
| sending | HTTP 409 — запит ще обробляється |
| failed або uncertain | Код переводить запис у sending і повторює відправлення в 1С |

**Поточне обмеження:** статус uncertain означає, що результат не визначений. Повторне надсилання з цього стану зараз дозволене кодом, тому за втраченої відповіді після фактичного створення документа можливий дубль у 1С. Описана ідемпотентність не є гарантією exactly-once. Це опис фактичної реалізації, а не твердження, що повтор із uncertain безпечний.

## 10. Telegram

### Успішна заявка

Для заявок саме із замірника створюється службовий стан `_measurement_telegram` у ResponseBody наявного запису. Celery надсилає повідомлення відповідальному менеджеру й копію користувачу `716230412`; якщо це одна адреса, дубль не надсилається.

У повідомленні: дилер, номер заявки, кількість конструкцій, GUID та коментар. Завдання спочатку фіксує початок надсилання у БД. Очікування обробляються також щохвилинним завданням. Помилка Telegram не скасовує успішне створення прорахунку. Стани доставки записуються окремо для адресатів.

### Відхилений або невдалий запит

Використовується бот помилок порталу: `PORTAL_ERROR_TELEGRAM_BOT_TOKEN` і `PORTAL_ERROR_TELEGRAM_CHAT_ID`. Сповіщення охоплює помилки API 4xx/5xx та явний `success=false`, зокрема ще до створення документа: немає user_id, користувач не дилер, немає UserId1C, недійсний ключ, некоректні файли або збій 1С.

Повідомлення містить ID помилки, HTTP-код, номер заявки, переданий ID користувача та безпечну причину. Ідентифікатори з тіла читаються лише після перевірки ключа інтеграції. Однакові помилки за кодом/причиною/ID групуються на 5 хвилин. Ключі, Base64 й довільні відповіді 1С у повідомлення не потрапляють.

Деталі: [MEASUREMENT_FAILURE_ALERTS_UA.md](MEASUREMENT_FAILURE_ALERTS_UA.md).

## 11. Налаштування

На порталі в `backend/.env`:

```dotenv
MEASUREMENT_API_KEY=<спільний секрет інтеграції>
MEASUREMENT_APP_ORIGIN=https://zamir.viknastyle.com.ua
ONE_C_URL=<адреса робочої публікації 1С>
ONE_C_USER=<серверний користувач 1С>
ONE_C_PASSWORD=<серверний пароль 1С>
PORTAL_ERROR_TELEGRAM_BOT_TOKEN=<токен бота помилок порталу>
PORTAL_ERROR_TELEGRAM_CHAT_ID=716230412
NOTIFICATION_TELEGRAM_BOT_TOKEN=<токен сповіщень менеджерам>
```

Той самий секрет на сервері Laravel використовується як `PORTAL_API_KEY`: ним замірник перевіряє SSO-підпис та авторизує запити в портал. Портальна адреса для Laravel — `PORTAL_URL=https://portal.vstg.com.ua`.

`MEASUREMENT_APP_ORIGIN` включений у CORS/CSRF-параметри Django; це не замінює JWT або X-API-KEY. У React origin замірника зараз окремо зафіксований константою `ZAMIR_ORIGIN`: однієї зміни .env для перенесення замірника на інший домен недостатньо.

В Apache порталу `frame-src` має дозволяти `https://zamir.viknastyle.com.ua`. Для камери потрібен дозвіл у Permissions-Policy; `camera=()` блокує її навіть за iframe `allow="camera; clipboard-write"`. На стороні Laravel вбудовування має бути дозволене для origin порталу. Налаштування заголовків на одному сервері не скасовує обмежень іншого.

## 12. Що зараз не автоматизовано

- Пряме читання БД замірника та звірка її статусів із 1С.
- Автоматичний вхід службовим логіном/паролем на сторінки `/requests/...`.
- Періодична перевірка, чи документ після успіху провели, видалили або змінили.
- Автоматична побайтова звірка збережених PDF/фото після кожної заявки.

За поточним рішенням користувача залишено прості сповіщення про невдалі запити. Наявність документа, його поточний стан та реальні файли можна перевіряти окремо за GUID; це інша перевірка, ніж успішна відповідь API.
