Стан: **відкрито тільки ролі `admin`** за вказівкою користувача 29.10.2026.
Сторінка `/statistics/reconciliation`, API `/api/dealer-reconciliation/`.
Кнопка «Звіт керівника · новий портал» є лише для адміністраторів у звітах
`/orders-report` та `/statistics/reports`. Маршрут виключений із managerRoutes,
branchLeaderRoutes та відсутній у dealerRoutes. Сторінка перевіряє isSuperAdmin;
API перевіряє точну роль admin до читання SQL, кешу або формування експорту.

## Погоджений склад

Заявки (прорахунки) нового порталу → пов’язані замовлення, для кожного етапу
кількість документів і конструкцій. Усі статуси, а «Подтверждено» - окремий
підсумок усередині загальної кількості. Поділу дилерів на самостійних і менеджерів
немає. Статус належить документу, а не дилеру.

Заявки звіту - документи `_Document44856`; кількість конструкцій `_Fld44861`,
власний стан `_Fld44862RRef`. На порталі ці заявки називають прорахунками;
це не окремий додатковий лічильник документів.

Замовлення: `Документы.ЗаказПокупателя`, конструкції `БВ_КоличествоКонструкций`,
стан `БВ_СостояниеЗаказа`, назви зі `Справочники.БВ_СостоянияЗаказов`.
Звітуються всі стани, включно з непроведеними документами. Позначені на
видалення виключаються. Підтвердження визначається точним GUID стану
`0x99B94EA6CCA98189497428BD64C2692D` («Подтверждено»); «Рисунок - подтвержден»
до цього підсумку не належить. Ознака проведення зберігається окремо.

## Період і склад дилерів

- `date_from`, `date_to`: період дат документів включно, локальний час Києва.
- `activity_from`: типово три календарні місяці до кінцевої дати; не пізніше
  початку звітного періоду. Максимальна глибина 366 днів.
- Рекурсивні фактичні папки `ДИЛЕРА` та `ФІЛІАЛИ / ЛЬВІВСЬКИЙ ФІЛІАЛ`.
  Група доступу не використовується. «Рута Магазин» належить Чернівецькій області.
- Дилери з замовленнями періоду активності або заявками звітного періоду плюс
  усі 74 GUID продзвону та додатково Журавецький, навіть без документів.
- Організація замовлень «Вікна Стиль»; виключені префікси 33-, 34-, 70-, 71-.
- Ознака заявки нового порталу: автор-контрагент (`_Fld44966_RTRef=0x0000007a`,
  GUID автора дорівнює GUID контрагента) або погоджений історичний GUID
  пов’язаного замовлення нового порталу. Виправлення й зіставлення назв збережені
  у приватному `records/data/dealer_reconciliation.json`, телефонів у ньому немає.
- Звіт не підключається до старого порталу і не показує його показників.

## Метрики без дублів

Головний блок відбирає заявки за датою створення. Беруться пов’язані замовлення
до кінцевої дати (у межах завантаженого періоду активності), зі зв’язків обох
напрямків. Перевіряється збіг GUID контрагента заявки та замовлення.
Кожна заявка і кожне замовлення рахуються за унікальним GUID. Зв’язок 1:N або
M:N не множить кількість конструкцій у підсумках дилера, області й усього звіту.
У деталізації замовлення видиме під усіма пов’язаними заявками.

Конверсія = заявки з хоча б одним підтвердженим замовленням / усі заявки.
Окремо - заявки без будь-якого замовлення. Підтверджені замовлення/конструкції
входять до загальних замовлень/конструкцій; додавати підсумки не можна.
Різниця конструкцій не означає відмову: зміни кількості можливі при оформленні.

Контрольний блок за датою замовлення показує всі замовлення в 1С, підтверджені
та віднесені до нового порталу. Він відрізняється від когорти заявок.
Статуси актуальні на момент формування, а не на історичну дату кінця періоду.
Повторний розрахунок того самого періоду може змінитися після редагувань у 1С.

## Експорт і перевірка

Знімок даних 30 хв у Redis DB 4, префікс `dealer-management-v3`, прив’язаний до
ID адміністратора. PDF/CSV використовують той самий знімок і фільтри області та
пошуку. Маршрут доступний лише авторизованим адміністраторам.

PDF: головні показники, графік конструкцій, окремі таблиці статусів заявок та
замовлень, регіони, дилери. CSV: один рядок на документ із типом, GUID, номером,
датою, власним статусом, кількістю конструкцій та номерами пов’язаних документів.
Сума конструкцій CSV має сенс тільки з фільтром типу документа: заявка й замовлення
є різними етапами, їх не слід додавати разом.

```bash
PYTHONPATH="$PWD/backend" venv/bin/python -m django test records.test_dealer_reconciliation --settings=backend.settings --noinput
cd frontend
node src/utils/dealerReconciliation.test.mjs
npx eslint src/pages/DealerReconciliationPage.jsx src/utils/dealerReconciliation.js
node_modules/.bin/esbuild src/pages/DealerReconciliationPage.jsx --bundle --format=esm --outfile=../tmp/manager-report-ui-check.js
```

SQL-зміни та міграції не потрібні. Зібрати frontend через npm run build та
перезапустити локальний ordersportal.service після оновлення backend.

## Мобільний вигляд і порівняння кожної заявки

На екранах до 700 px таблиці нового звіту переходять у картки з підписами.
Дата та пошук мають шрифт 16 px, кнопки щонайменше 44 px. Контрастна кнопка
«Сформувати звіт» має окремі кольори для світлої й темної тем. Деталізація заявок
доступна загальним списком і в діалозі дилера, з пошуком і сторінками по 20 заявок.
У картці видно конструкції заявки, кількість пов’язаних замовлень, конструкції
в них та окремо таблицю кількостей/конструкцій за статусами цих замовлень.

CSV `export=csv&dataset=applications` - один рядок на заявку: її конструкції,
кількість замовлень, конструкції замовлень, підтверджені та зведення за статусами.
Якщо одне замовлення пов’язане з кількома заявками, воно видиме в кожній картці;
загальний підсумок звіту дедуплікує GUID. Тому сума колонок замовлень по заявках
у цьому CSV може перевищувати загальний унікальний підсумок. Звичайний
`export=csv` зберігає попередній формат - один рядок на документ.
