# Новий портал: заявки та конструкції

Сторінка адміністратора: `/statistics/reconciliation`. Кнопка входу також є
на `/statistics/reports`: «Новий портал: заявки та конструкції · PDF».
API: `GET /api/dealer-reconciliation/` (лише роль `admin`).

## Формування

- `date_from`, `date_to`: звітний період включно, за місцевим часом порталу.
- `activity_from`: початок відбору активних дилерів (типово три календарні місяці
  до кінцевої дати). Максимум 366 днів; не пізніше початку звітного періоду.
- Фактичні папки контрагентів: `ДИЛЕРА` та всі вкладені папки; окремо
  `ФІЛІАЛИ / ЛЬВІВСЬКИЙ ФІЛІАЛ`. Група доступу не використовується.
- Дилери з підтвердженими замовленнями за період активності плюс усі 74 GUID
  продзвону та Журавецький. Усі 75 залишаються навіть без замовлень.
- Замовлення: організація «Вікна Стиль», точний стан «Подтверждено», проведені,
  не позначені на видалення. Виключено префікси 33-, 34-, 70-, 71-.
- Це поточний стан документів на момент формування. Зміни станів у 1С можуть
  змінити результат повторного формування за тим самим минулим періодом.

## Метрики

`_Document44856._Fld44861` — конструкції в заявці;
`Документы.ЗаказПокупателя.БВ_КоличествоКонструкций` — у замовленні.
Заявки проведені, не видалені, створені у звітному періоді. Ознака нового
порталу: автор-контрагент (`_Fld44966_RTRef=0x0000007a`, GUID автора дорівнює GUID
контрагента), або пов’язане замовлення з погодженою раніше класифікацією «новий
портал». У поточному коді портал надсилає GUID контрагента як автора і для дилера,
і для менеджера: це не ідентифікатор фактичної людини.

Поділу дилерів і конструкцій на «Самостійно» та «Менеджер» немає.
Усі показники загальні; доступні лише фільтри області / філіалу та пошук дилера.
Збережено погоджений склад вибірки, реєстрації та перенесення акаунтів.
«Рута Магазин» включено до Чернівецької області. Відповідності GUID зберігаються
у приватному `backend/records/data/dealer_reconciliation.json`, без телефонів
і підсумків. Додатковий контрагент Журавецький збережений у `additional_dealers`.

Порівняння заявок: усі заявки звітного періоду → пов’язані підтверджені замовлення
до кінцевої дати відбору (зі зв’язків обох напрямків). Конверсія = кількість заявок
із хоча б одним підтвердженим замовленням / усі заявки. Одне замовлення рахується
один раз у підсумках дилера, області й усього звіту, навіть за кількох зв’язків.
У деталізації воно видиме під кожною пов’язаною заявкою: рядки CSV не слід
підсумовувати як унікальні замовлення. Різниця конструкцій не є ознакою відмови.

Окремий блок замовлень за датою замовлення показує всі підтверджені в 1С та
віднесені до нового порталу. Його суми можуть відрізнятися від когорти заявок.
Звіт не підключається до старого порталу і не відображає його показники.

## Експорт і однакові цифри

Після формування API повертає `snapshot`. Знімок зберігається 30 хв у Redis DB 4
із префіксом `dealer-constructions-v2`, із прив’язкою до ID адміністратора.
Усі workers використовують спільний Redis, як Celery/channels існуючого порталу.
PDF/CSV беруть саме цей знімок; дані SQL вдруге для експорту не читаються.
Запити: `?snapshot=...&export=pdf` або `export=csv`.
Фільтри `region`, `search` однакові для екрана та експорту.
Після закінчення знімка API повертає 410 із пропозицією повторно сформувати звіт.

PDF містить підсумки, графік, дилерів і таблицю заявка → замовлення. CSV містить
повну деталізацію заявок. Дані отримуються лише SELECT/CTE; міграції не потрібні.

## Перевірки

З кореня проєкту:

```bash
PYTHONPATH="$PWD/backend" venv/bin/python -m django test records.test_dealer_reconciliation records.test_dealer_report_groups records.test_deliveries_pdf --settings=backend.settings --noinput
cd frontend
node src/utils/dealerReconciliation.test.mjs
npx eslint src/pages/DealerReconciliationPage.jsx src/utils/dealerReconciliation.js
npm run build
```

Після оновлення backend перезапустити локальний `ordersportal.service`.
На SQL Server нічого встановлювати або змінювати не потрібно.
