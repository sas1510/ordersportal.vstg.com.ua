# Сповіщення про невдалі заявки із замірника

Після POST /api/integrations/measurement/orders/ портал надсилає сповіщення про HTTP 4xx/5xx та явну відповідь success=false. Перевірка охоплює відмови авторизації та валідації до створення документа.

Причини: не дилер; відсутній/некоректний user_id; користувач відсутній або неактивний; прострочений доступ; немає UserId1C; недійсний ключ інтеграції; некоректні дані чи вкладення; конфлікт повторного запиту; помилка 1С або неналаштована інтеграція. Права створення документів не змінюються: лише дилери/customer із прив’язкою до контрагента.

Призначення — чинні PORTAL_ERROR_TELEGRAM_BOT_TOKEN та PORTAL_ERROR_TELEGRAM_CHAT_ID, тобто бот помилок порталу. При відсутніх налаштуваннях повідомлення не надсилається. Нових ключів чи таблиць не потрібно.

Повідомлення: ID помилки, шлях API, HTTP-код, переданий ID користувача, номер заявки (якщо передано), безпечний опис причини. Ідентифікатори з тіла читаються лише після перевірки ключа інтеграції. Тіло запиту/відповіді, Base64, паролі й ключі не надсилаються.

Однакові помилки для одного ID та HTTP-коду групуються на 5 хвилин через Django cache. Успішні заявки зберігають наявні сповіщення відповідальному менеджеру та копію. Збій надсилання сповіщення не змінює відповідь API.

Це спрощений варіант: автоматичний вхід до замірника, звірка його БД та фонове читання файлів 1С не запускаються. Документ, який згодом позначили на видалення після успішної відповіді, ця перевірка не відстежує.

Після перенесення коду на сервер перезапустити backend:

```bash
sudo systemctl restart ordersportal.service
```

Міграції БД та збірка фронтенду для цього сповіщення не потрібні. Код підготовлено локально; на робочий сервер у цій зміні не розгортався.

Перевірено 61 тестом SSO, API, сповіщень та відмов доступу; мережеві відправлення і створення тестових документів у 1С під час тестів замінено моками.
