# Тестові V7/V8 без нових постійних індексів

Дата: 27.10.2026. Сервер: WST\WST, база: portal_db.

Створено й виконано окремі процедури:

- dbo.GetCalculationsWithOrdersByYearAndContractor7_NoNewIndexesTest
- dbo.GetOrdersMonthWithCalculations8_NoNewIndexesTest

Портал продовжує використовувати свої поточні процедури. Визначення робочих V7/V8 до та після експерименту порівняно: не змінилися. Нових постійних індексів не створено. Тимчасові таблиці та їхні тимчасові індекси з оригінального алгоритму збережено.

## Зміни

1. У тестовій V8 прибрано чотири примусові підказки INDEX(_Document381_ByDocDate_TRL), FORCESEEK. Оптимізатор може використовувати інші наявні індекси або сканування. У живій V7 на момент створення копії цих підказок уже не було; їх там не змінювали.
2. В обох тестових процедурах надходження за COALESCE(NULLIF(ЗаказПоставщику, нульове посилання), Заказ) розділено на дві взаємовиключні гілки UNION ALL: пряма прив’язка до ЗаказПоставщику та запасна прив’язка до Заказ лише за відсутнього/нульового ЗаказПоставщику. Це прибирає функцію навколо індексованого посилання. Нульове посилання в першій гілці виключено; дублювання між гілками неможливе.
3. Перевірки проведення, видалення, товару/характеристики, кількості та повернень збережено. Жодного фільтра власника характеристики не звужували: його звуження до поточних замовлень могло б помилково визначити готовність.

## Перевірки

Порівнювали всі значення всіх стовпців як мультимножину рядків: порядок однакових ключів сортування не впливає на перевірку, повтори враховуються. Дані користувачів не включено до JSON-вимірювань.

| Сценарій, 01–27.10.2026 | Рядків | Читань робочої | Читань тестової | Зменшення |
|---|---:|---:|---:|---:|
| Дилер | 14 | 233 352 | 214 890 | 7,9% |
| Менеджер | 408 | 1 110 891 | 513 935 | 53,7% |
| Адміністратор | 2822 | 1 399 392 | 802 614 | 42,6% |

Числа — сума logical reads із STATISTICS IO, включно з проміжними таблицями. Повтор у зворотному порядку дав практично ті самі читання. JSON comparison.json та comparison_reverse.json містять заміри. Останній звіт містить 2822 рядки проти 2818 під час попереднього аудиту: джерело активно змінюється.

Час коливається. Менеджер: робоча 1,75–2,11 с, тестова 1,51–1,61 с у виміряних парах. Для дилера та адміністратора стабільного виграшу за часом поки не доведено: у зворотному запуску тестова була дещо повільнішою, попри менше читань. Кеш сервера не очищували.

Повний збіг отримано для дилера й менеджера та в контрольному порівнянні адміністратора. У двох інших парах адміністратора був один рядок із відмінними CalcState/OrderStage. Обидва поля походять із початкового розрахунку, до зміненої ділянки надходжень. Контроль робоча–тестова–робоча дав повний збіг усіх трьох результатів; повтор робоча–робоча також збігся. Причину одиничних yjvth відмінностей на живому READ UNCOMMITTED остаточно не встановлено. Для остаточного допуску потрібне порівняння на незмінній копії даних; не вважати ці заміри підставою для автоматичної заміни робочих процедур.

Фактичні плани тестових процедур знято. Найбільший залишковий обсяг — сканування рядків замовлень для глобальної перевірки власника характеристики; без нового індексу його не усунуто.

## Файли й повторний запуск

У цій папці: *_baseline.sql — знімки живих визначень перед експериментом; *_NoNewIndexesTest.sql — встановлені тестові визначення; JSON — вимірювання без даних замовлень.

Тестові процедури мають ті самі параметри, що й робочі. Для дилера: @DateFrom, @DateTo, @Contractor_ID BINARY(16). Для звіту: @RequesterUserID, @DateFrom, @DateTo, @DealerGroup.

Кожен *_NoNewIndexesTest.sql виконується окремим SQL batch у portal_db, містить CREATE OR ALTER лише тестової процедури. Портал на них не перемикали. Для видалення експерименту використайте DROP_TEST_PROCEDURES.sql. Робочі знімки не виконувати без окремого рішення.
